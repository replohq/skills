# Intelligems

Set up, inspect, or evaluate Intelligems experiments on Replo pages. Analyze existing Intelligems data and build split URL tests, content variations, or price tests on or including Replo pages.

Use this guide when a merchant wants a Replo page in an Intelligems test, wants variations on one Replo URL, or asks about an Intelligems experience or its results. For site implementation, read the `building-replo-pages` skill; for local editing and publishing, use the public local-development and publishing skills. Discover the connected Intelligems operations in your available public MCP tools and follow their schemas. If the required operation is unavailable, ask the merchant to provide the experiment IDs or perform that step in Intelligems; do not assume access to internal Replo tools.

To use Intelligems on a Replo site, always install `@intelligems/headless` in that site and configure its provider and tracking hooks. This applies to on-page tests, Replo URLs in Split URL tests, pricing and custom events. For journeys crossing Replo and Shopify hosts on a shared domain, apply the [required 1.2.19 package patch](references/package-patch.md) and set its `cookieDomain` prop, or verify a vendor-fixed release before proceeding.

The connected Intelligems External API token gives management and reporting tools. It does **not** install visitor assignment or tracking on a published page. First identify the tested origin, each variation URL or section, the store's domain, and whether attribution must include cart and checkout.

During implementation and before publishing, run the [code audit](references/code-audit.md) against the site source and local dev server. When asked to verify the published setup, or before declaring a test ready for traffic, run the separate [live experiment audit](references/live-experiment-audit.md). Report the two results separately; a code pass or HTTP 200 alone does not prove order attribution. For quiz, lead, or selected CTA goals, read [Intelligems’ headless custom-events documentation](https://headless.intelligems.io/examples/custom-events). Do not track every click by default.

## Replo URL as a variation

1. Publish the Replo destination on a merchant-owned subdomain such as `lp.brand.com` when the origin is `www.brand.com`. Intelligems does not support redirect tests or persistent assignment across unrelated registered domains; a `*.replosites.com` destination will not carry the origin's assignment.
2. Configure an Intelligems **Split URL** (`content/url`) experience with the entry page as the origin and the Replo page as a variation destination. The Replo connection can create a pending test shell, but URL routing still needs to be configured in Intelligems. Have the merchant finish those fields in Intelligems before starting the test.
3. Keep Intelligems installed on the origin. Install `@intelligems/headless` on the Replo destination and configure its provider and tracking hooks. The Replo connection alone does not load a script or SDK. Check existing tags first; do not run the standard Intelligems script and the headless SDK on the same Replo page.
4. In a fresh browser session, visit the origin, follow the redirect, verify the assigned variation and destination page view, complete a test checkout, and verify the order appears under the correct variation. Visiting the destination directly may not join that redirect test.

The Split URL redirect runs after the origin begins loading in the browser, adding a page load for the destination variation. Account for that in performance-sensitive comparisons. The headless SDK does not provide a server-side visitor assignment endpoint or HTTP redirect.

Verify Intelligems' configured cookie domain in the **published CDN configuration**, not just the account settings UI. With headless 1.2.19, a fresh visit to Replo can create a host-scoped `ig-id`; a subsequent Shopify visit can then create a different visitor ID even on sibling domains. A Shopify-first visit with the standard script configured for the registered domain can carry its identity into Replo. Test both directions and direct entry separately. Use the [tested package patch](references/package-patch.md) for this initialization bug; do not replace it with ad-hoc cookie writes or runtime mutations of private SDK internals. Verify continuity in the published setup before claiming it works.

## Content variations on one Replo URL

Follow Intelligems' [Next.js App Router guide](https://headless.intelligems.io/integration-guides/next.js-or-app-router). Install `@intelligems/headless` in the site and use `IntelligemsNextClientsideAppDirectoryProvider` with `organizationId`, `storefrontApiToken`, and `activeCurrencyCode`. Put a client component under it that calls `useIgVariation(experienceId)` and renders the matching section. Keep the tested section neutral until `isReady` so the visitor does not briefly see the wrong version. Assignment happens after hydration; it cannot run in a Replo data loader or Server Component.

Ask for the merchant's Intelligems organization ID. Load the connected store's browser-safe Storefront token with `ShopifyIntegrationDetailsLoader` from `@replohq/sdk/loaders/shopify-integration-details-loader`, inside `ReploProvider`. Set `loaderKey={DATA_LOADER_KEYS.SHOPIFY_INTEGRATION_DETAILS}` using `@replohq/sdk/loaders/loader-keys`; the loader takes no arguments. Its child receives `{ shopifyDomain, storefrontAccessToken }`: verify the domain matches the intended store and pass `storefrontAccessToken` into the Intelligems provider's `storefrontApiToken` prop. Do not ask the merchant to copy a token. Optional server prefetch through `PrefetchedLoaders` uses the same key and `args: {}`. Give the loader usable default content as its fallback, outside the Intelligems provider. Only the public Storefront token belongs in the browser; never expose a Shopify Admin API token or the Intelligems External API token. Use the page's actual market currency and country.

Before writing the integration, inspect the installed `@replohq/sdk` types and confirm the integration details loader and key are exported and `useCart()` exposes `cartId`. Upgrade to a published release that includes it if needed; if no compatible release is available, report that blocker instead of generating code against an unpublished API.

For Shopify checkout attribution, call `useIgTrack({ cartOrCheckoutToken: cartId, currency: market.currencyCode, country: market.country })` under the Intelligems provider. `useCart()` from `@replohq/sdk/cart/cart-provider` supplies only the cart ID; place this component under `ReploProvider` too. Read the [implementation guide](https://docs.replo.app/developers/intelligems) for a cookie-selected market example. Resolve the selected market from the site's market-selection cookie on the server, validating its value against the merchant's configured market entries and falling back to the merchant's default for missing or unsupported values. Reuse the site's existing cookie name and resolver; there is no built-in selected-market cookie to assume. Each entry must provide the verified Shopify `{ country, currencyCode }`. Language is independent: never derive market or currency from `lang`, translation routes, or `replo-locale`. Verify the currency against the merchant's Shopify Markets configuration, since a country without international pricing can still use the shop default currency. Do not require a cart or product loader to determine currency; Intelligems must also work on content-only pages. Pass `market.country` to Shopify loaders, their prefetch arguments, and the existing `ReploProvider markets={{ shopify: { country: market.country } }}`. Pass `market.currencyCode` to Intelligems `activeCurrencyCode` and `useIgTrack`. After the market selector writes its cookie, refresh the server-rendered tree so all consumers receive the same updated market. If consent is enabled, mount the Intelligems provider and tracker only after hydration and after `isConsentAllowed({ state: useConsent(), requiredConsent: ["analytics"] })` returns true. Visitors who decline analytics see the default content and are not measured.

For a Shopify **Buy Now** button, the checkout uses a separate cart, so tracking the normal `useCart().cartId` does not attach experiment data to that checkout. In a component under the Intelligems provider, call `useIgCartAttributes()` and pass its `attributes` to `useBuyNow().buyNow(variants, { attributes })`. Wait for the hook's `isReady` before starting an attributed checkout. The SDK types attribute values as nullable: narrow values to strings and disable attributed checkout if any value is missing, rather than casting or silently dropping it. Pass the exact returned attributes; do not invent Intelligems keys or append `attributes[...]` to the checkout URL. If consent is declined, a normal Buy Now checkout can proceed without Intelligems attributes. Verify that the installed `@replohq/sdk` release supports the Buy Now `attributes` option before relying on it; older releases silently ignore the extra option. For shipping experiments, use `useIgCart().wrapCustomAttributes` for line item properties as well.

For price, shipping or offer tests, content selection alone is insufficient. Configure Intelligems' price/cart hooks and Shopify checkout integration before claiming purchase or revenue results. Verify assignment, page view, cart attributes and a test order before sending live traffic. The [Replo Intelligems guide](https://docs.replo.app/developers/intelligems) contains a component example.

When changing market, remount the Intelligems provider with a key containing the selected country and currency after refreshing the server tree. In headless 1.2.19, the client captures its active currency at construction; updating the prop alone is insufficient. Keep cart, loader and displayed prices aligned with the same market.

Use `isReady` for assignment loading and an error boundary with usable default content for thrown SDK errors. Keep the rest of the page usable while the tested section loads. Keep tracking behind assignment readiness and the decision to render the assigned content; never measure a treatment while default fallback content is visible. See the audit for the distinction between unmeasured fallback and an assigned control.
